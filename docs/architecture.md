# SPARK On-premises 架构提案：面向个人闲置设备的 LLM 联合部署

> 状态：v0.1 提案 + M1 实现。文中标注【未实测】的论断尚无基准数据支撑，
> 待 `benchmarks/results/` 补充。本文遵循与姐妹项目 prairie-fire 相同的诚实声明原则。

## 1. 问题定义

个人拥有的计算设备普遍呈现"异构、闲置、分散"三特征：

| 维度 | 现实情况 |
| --- | --- |
| 算力 | 从树莓派（4-8GB RAM, ARM）到独显 PC（24GB+ VRAM）跨 2 个数量级 |
| 网络 | 以 Wi-Fi 为主，千兆有线为辅；内网带宽 0.1-1 Gbps，延迟 1-10ms |
| 可用性 | 设备会合盖、休眠、断电、被拿走——不是机房里的稳定节点 |
| 运维能力 | 主人一个人，不可能维护 5 套不同的部署方案 |

目标：**在不新增硬件采购的前提下（降本），让这堆设备联合提供超出任何单机能力的 LLM 服务（升效），并且用一套共通方案部署到所有平台（省心）。**

## 2. 设计决策：编排层，而非新推理内核

我们不自研分布式推理算子，而是把 llama.cpp 当作"跨平台推理原语"，在其上构建编排层。理由：

1. llama.cpp 是唯一覆盖 Windows/Linux/macOS/Android(Termux)/树莓派 的成熟引擎，GGUF 生态完备；
2. 其 RPC 模式原生支持按各节点内存比例切分模型（驱动节点 + rpc-server 链）；
3. 推理内核的性能优化（量化、SIMD、GPU 后端）由上游社区持续迭代，编排层可直接受益；
4. 我们要验证的命题在调度与部署层：**放置决策、生命周期管理与共通部署才是闲置设备场景的真正瓶颈**，而不是算子级并行。

## 3. 架构总览

```
┌────────────────────────── 局域网 ──────────────────────────────┐
│                                                               │
│  用户/应用 ── OpenAI 兼容 API ──▶ spark-master (Python)        │
│                                    ├── Registry   设备注册表     │
│                                    ├── Planner    放置规划器     │
│                                    ├── Gateway    请求路由       │
│                                    └── Dashboard  Web 面板      │
│            UDP 广播自动发现 + HTTP 控制通道（agent 侧监听）        │
│   ┌──────────┬──────────┬──────────┬──────────┬──────────┐    │
│   │spark-agent│spark-agent│spark-agent│spark-agent│spark-agent│   │
│   │ Windows  │  Linux   │  macOS   │ 树莓派    │ Android   │   │
│   │ 监管 llama.cpp（rpc-server / llama-server） │ (Termux)  │   │
│   └──────────┴──────────┴──────────┴──────────┴──────────┘    │
└───────────────────────────────────────────────────────────────┘
```

组件职责：

- **spark-agent（Go，单文件二进制）**：设备侧守护进程。UDP 广播宣告存在与硬件清单；向 master 发心跳；接收 master 的控制指令（下载引擎/模型、启动/停止 worker）；监管 llama.cpp 子进程（崩溃重启、日志落盘）。
- **spark-master（Python/FastAPI）**：集群大脑与统一入口。维护设备注册表（TTL 惊逐）；运行放置规划器；把请求代理到活跃部署的 llama-server；托管 Web 面板。
- **推理平面**：llama-server（单机模式）或 驱动节点 llama-server + 多个 rpc-server（切分模式）。对上游完全无感——只看到一个 OpenAI 兼容端点。

## 4. "降本升效"四机制

### 4.1 分级放置（Tiered Placement）

规划器输入：模型注册表条目（GGUF 体积）× 设备清单（可用内存/后端能力）。输出两种放置模式：

- **单机模式（single）**：`max(可用内存) ≥ 模型体积 × 1.15 + 上下文余量` 时，部署到评分最高的单节点（评分 = 可用内存 + GPU 加分 + CPU 加分）。零网络开销，延迟最优。
- **切分模式（split）**：单机放不下时，按可用内存降序选取节点集合，直到累计内存覆盖模型体积 × 1.25；内存最大者为**驱动节点**（持有 GGUF 文件、运行 llama-server），其余运行 rpc-server，llama.cpp 按各节点内存比例分布权重与 KV cache。

**多模型共位（co-location，M1 已实现并实测）**：驱动节点可同时承载多个 llama-server 实例（每部署独立端口 `8300+`），规划器只对 rpc 角色节点做独占排除。2026-10-26 实测：单节点同时服务 qwen2.5-0.5b + qwen2.5-1.5b，统一网关按 `model` 字段路由。注意：并发部署期间心跳里的可用内存尚未反映加载中的模型，存在过提交风险（靠部署失败兜底，M2 引入内存预留记账）。

规划器是纯函数（清单 + 模型 → 计划），便于单元测试与后续替换为更聪明的策略（如带宽感知、负载感知）。【成本模型中的放大系数 1.15/1.25 目前为工程经验值，未实测校准】

### 4.2 闲置设备生命周期（Lifecycle）

闲置场景的"降本"核心不是算得更快，而是**不用的设备不耗电**：

- 心跳 TTL（默认 15s）判定离线；部署依赖的节点离线 → 部署标记 degraded，网关返回可重试错误（M1）；自动重分片到剩余节点（M2）。
- 空闲休眠策略（M2）：未被任何部署使用超过 N 分钟的设备下发休眠；需要扩容时通过 Wake-on-LAN 唤醒（agent 清单上报 MAC 地址）。
- 冷启动预算：唤醒 + 引擎启动 + 模型加载的时长记入部署成本，规划器避免为小请求唤醒整集群（请求排队 vs 唤醒的权衡，M2 设计）。

### 4.3 异构感知（Heterogeneity-aware）

- 清单维度：OS/架构、CPU 核数与型号、总内存/可用内存、数据盘剩余、GPU 探测（best-effort）、外网可达性。
- 后端选择：同一份 GGUF，Windows x64 用 avx2 构建，树莓派用 arm64 构建，macOS 用 arm64（Metal）；【GPU 自动探测与 `-ngl` 自动设置：M2】。
- 网络 best-effort 探测（M2）：节点间带宽影响切分收益，规划器可将"带宽过低"降级为"仅单机模式"。

### 4.4 故障自愈（Self-healing）

- worker 子进程崩溃：agent 监管器自动重启（指数退避，上限 3 次），上报 master。
- 节点级故障：注册表 TTL 惊逐 → 部署降级；M2 实现自动重规划（在剩余节点上重建 rpc 链与驱动节点，模型文件按需重新分发）。
- 语义保证：网关对受影响请求返回 `503 + Retry-After`，不静默吞错。

## 5. 性能模型（定性）

多机切分的收益与代价：

- **收益**：可运行单机装不下的模型（内存聚合）；prefill 阶段各节点并行计算各自层【加速比未实测】。
- **代价**：decode 阶段每 token 需跨节点串行传输激活值，吞吐受最慢链路制约。经验上 Wi-Fi（≈0.1-0.3 Gbps）会显著拖慢 decode，有线千兆是舒适区【未实测，待 benchmarks/验证】。
- **结论（预期）**：切分模式的定位是**"跑得起来" > "跑得快"**——用时间换可行性；对延迟敏感的小模型应走单机模式。这正是分级放置存在的理由。

所有定量结论以 `benchmarks/` 可复现脚本产出为准。

## 6. 安全模型

v1 信任模型：**可信局域网**。master 与 agent 的控制通道明文 HTTP，任何同网设备可加入集群（类似 Samba/家庭 NAS 的默认信任级别）。M2 引入共享令牌（`SPARK_TOKEN` 环境变量，控制通道头部校验）。明确不建议将 master 端口暴露到公网；需要远程访问时应走 VPN/Tailscale 类隧道。

## 7. 与姐妹项目的关系

prairie-fire 研究"协作训练如何在跨设备协商开销受限时仍然收敛"（参数存储与协商开销的数学结构）；本项目回答对偶问题——"协作推理如何在不稳定异构设备上仍然可用"。两者共享同一立场：**个人算力被系统性低估，值得一个严肃的工程/研究框架**。长期愿景（roadmap M5+）：推理侧为训练侧提供梯度通信之外的"参数面"基础设施，两仓库在协议层互通。
